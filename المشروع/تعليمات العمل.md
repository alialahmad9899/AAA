# تعليمات العمل الثابتة — Backend / Laravel / API

هذه التعليمات إلزامية لهذا الجزء من وصال، وتُقرأ مع ملف `/AGENTS.md` و`/PROJECT_NOTES.md` قبل كل مهمة.

## نطاق العمل المعتمد — أولوية قصوى
**الهدف هو تطبيق وصال للموبايل ولوحة تحكم الأدمن فقط. الموقع العام وواجهات الأعضاء في الويب خارج نطاق العمل.**

- نفّذ التعديلات التي تخدم تطبيق Flutter للموبايل: API، منطق Backend، التحقق من البيانات، الصلاحيات، التخزين، الإشعارات، الاشتراكات، والربط مع قاعدة البيانات بحسب الحاجة المثبتة.
- يُسمح بتعديل Laravel API والملفات الخلفية المشتركة التي يعتمد عليها التطبيق، بعد تتبع الاستدعاء من التطبيق إلى المسار والـController والـModel وقاعدة البيانات.
- يُسمح بتعديل **لوحة تحكم الأدمن فقط** عندما يطلب المستخدم ذلك، أو عندما تكون هناك حاجة تشغيلية واضحة ومثبتة لإدارة ميزة تخص التطبيق.
- لا تعدّل الموقع العام أو واجهات الأعضاء: لا صفحات الزوار أو الأعضاء، ولا واجهات Blade الخاصة بالموقع، ولا CSS/JS أو الأصول أو التصميم أو SEO أو التوافق مع الشاشات الخاصة به.
- لا تنفّذ تحسينات أو إصلاحات للموقع لمجرد أن ملفات الموقع موجودة في المستودع. وجود الملف لا يجعله ضمن النطاق.
- لا تغيّر Web Routes أو Web Controllers أو واجهات الموقع العامة عند معالجة مشكلة في الموبايل. ابحث أولاً عن مسار API الذي يستدعيه التطبيق.
- عند وجود ملف Laravel مشترك بين API ولوحة الأدمن أو بين أكثر من قناة، افحص الاستخدامات والأثر الجانبي ولا تغيّر سلوكاً خارج النطاق دون ضرورة موثقة.
- الموقع الحالي مخطّط لإيقافه تدريجياً مستقبلاً والإبقاء على تطبيق الموبايل ولوحة الأدمن. لا تنشئ ميزات جديدة مرتبطة بالموقع العام، لكن لا تحذف أو توقف الموقع أو قواعده أو ملفاته الآن دون طلب صريح.
- إذا كان الطلب غامضاً بين التطبيق ولوحة الأدمن والموقع، اعتمد التطبيق كوجهة افتراضية، واسأل فقط إذا تعذّر حسم النطاق من السياق.

## القاعدة غير القابلة للتجاوز: عدّل الأصل في مكانه
- المصدر المعتمد هو آخر نسخة من الملف الأصلي في فرع العمل الحالي بالمستودع.
- نفّذ الإصلاح مباشرة على الملف الموجود في مساره الحالي داخل `المشروع/WESAL/`; لا تنشئ نسخة بديلة ولا تطلب استبدال الملف الأصلي لاحقاً.
- ممنوع إنشاء مجلدات مثل «إصلاحات» أو «إصلاحات 2» أو `patches` أو `fixed` أو وضع ملفات معدلة موازية خارج مساراتها الأصلية.
- الملف الجديد مسموح فقط عند ضرورة تقنية مثبتة، مثل اختبار أو مكوّن جديد، ويجب وضعه في المسار الطبيعي للمشروع لا كمجلد تسليم.
- لا تعتبر الأرشيفات القديمة أحدث من ملفات الفرع؛ افحص آخر Commit وGit diff قبل التعديل.

## طريقة العمل
- اقرأ `/AGENTS.md` و`/PROJECT_NOTES.md` وهذه التعليمات أولاً.
- افحص Route وMiddleware وController وRequest وModel وRelationship وResource ومصدر بيانات قاعدة البيانات ذات الصلة.
- اثبت السبب الجذري من الكود أو سجل الخطأ أو اختبار قابل لإعادة الإنتاج.
- حافظ على منطق الصلاحيات وعزل بيانات الأعضاء والتحقق من المدخلات وتوافق الاستجابات.
- نفّذ أقل تغيير آمن، واختبر PHP syntax والاختبارات المناسبة، ولا تدّعِ فحص قاعدة بيانات أو استضافة حية دون تنفيذ فعلي.

## سجل الدفعات
- أضف ملخص الدفعة في نهاية `/PROJECT_NOTES.md` الموجود؛ لا تنشئ سجل إصلاحات آخر ولا تستبدل الملاحظات السابقة.
- اذكر السبب الجذري، المسارات الأصلية التي تغيرت، الإصلاح، الاختبارات، وما لم يتم التحقق منه.

## ZIP إلزامي بعد كل جلسة إصلاح
- بعد كل طلب إصلاح برمجي تُنفّذ فيه تعديلات فعلية، أنشئ ZIP تلقائياً وسلّمه للمستخدم في الرد نفسه حتى لو لم يطلبه صراحة. لا تنتظر تذكيراً منفصلاً.
- يجب أن يحتوي الأرشيف على ملفات Laravel/API والإعدادات والاختبارات التي تغيّرت في هذه الجلسة فقط؛ لا تخلط إصلاحات جلسات سابقة ولا تضم المشروع كاملاً.
- احتفظ بالمسارات النسبية الأصلية ابتداءً من جذر ZIP، ولا تضف مجلداً تغليفياً عاماً مثل «إصلاحات».
- استبعد تعليمات المستودع و`PROJECT_NOTES.md` من حزمة استبدال ملفات التشغيل؛ حدّثها داخل Git فقط ما لم يطلب المستخدم تضمينها.
- أنشئ ZIP خارج المستودع كملف تنزيل مستقل، ولا تضف أرشيفات التسليم إلى Git.
- تحقق من سلامة الأرشيف وعدد الملفات والمسارات ومطابقة محتوياتها لآخر Commit في فرع الجلسة، واذكر Commit المصدر وارفق رابط التحميل في الرد النهائي.
- إذا لم تتغير ملفات تنفيذية أو تعذر التحقق من ZIP، صرّح بذلك ولا تنشئ رابطاً وهمياً.
## Git والنشر
- اعمل على فرع العمل المتفق عليه. لا تغيّر `main` ولا تدمج ولا تنشر إلى الاستضافة دون طلب صريح.
- وضّح دائماً الفرق بين فحص محلي/CI وفحص حي على الاستضافة.


## دمج آخر نسخة لكل ملف — إلزامي
- عند وجود أكثر من نسخة معدّلة للمسار نفسه في فروع أو دفعات مختلفة، اقرأ سجل `PROJECT_NOTES.md` وقارن آخر تعديل لكل فرع، ثم اعتمد النسخة النهائية الأحدث لذلك المسار.
- لا تستبدل ملفاً حديثاً بنسخة فرع أقدم. انقل فقط الإصلاحات السابقة التي لا تزال مطلوبة وغير موجودة في النسخة الأحدث، مع دمجها داخل الملف الحالي.
- لا تعتبر ZIP أو فرعاً قديماً أساساً كاملاً؛ الدمج يكون ملفاً بملف بعد فحص التداخل والأثر على المستهلكين.
- يبقى `main` هو المصدر الأساسي بعد الدمج والتحقق. أي تعديل جانبي يجب أن يعود إليه قبل تسليم نسخة كاملة للنشر.
