# تعليمات العمل الثابتة — Flutter / Dart

هذه التعليمات إلزامية لهذا الجزء من وصال، وتُقرأ مع ملف `/AGENTS.md` و`/PROJECT_NOTES.md` قبل كل مهمة.

## نطاق العمل المعتمد — أولوية قصوى
**العمل الأساسي هو تطبيق وصال للموبايل فقط. لا نطوّر الموقع العام ولا واجهات الأعضاء في الويب.**

- اعتبر مجلد `فلاتر/` هو المسار الأساسي لتطوير واجهة التطبيق وسلوكه وتجربة المستخدم على Android وiOS.
- ركّز على شاشات التطبيق وتدفق التسجيل والدخول والملف الشخصي والمحادثات والإشعارات والاشتراكات والبطاقات والتنقل والأداء والاستقرار والأمان.
- عند احتياج التطبيق إلى تعديل خلفي، انتقل إلى Laravel API والـBackend داخل `المشروع/WESAL/` بالقدر الضروري فقط لخدمة التطبيق، مع عدم تعديل واجهات الموقع العام.
- لا تنفّذ تعديلات متوازية للموقع أو صفحات الأعضاء أو واجهات Blade/CSS/JS. لا تجعل تحسين الموقع جزءاً من إصلاح التطبيق.
- لوحة تحكم الأدمن خارج مجلد Flutter، ويُسمح بتعديلها فقط بطلب واضح أو لحاجة تشغيلية مثبتة لإدارة التطبيق؛ الأولوية تبقى للموبايل.
- إذا كان الخلل يظهر في التطبيق، افحص التنفيذ على الموبايل أولاً، ثم تتبّع API الفعلية التي يستدعيها التطبيق. لا تفترض أن وجود وظيفة مشابهة بالموقع يعني أن التطبيق يستخدمها.
- الموقع مخطّط لإيقافه تدريجياً، مع الإبقاء على تطبيق الموبايل ولوحة تحكم الأدمن. لا تُنشئ ميزات جديدة للموقع، ولا تحذف أو تعطل أجزاء منه دون طلب صريح.
- عند غموض النطاق، اعتبر أن المطلوب هو تطبيق الموبايل، ولا تنتقل إلى الموقع العام.

## القاعدة غير القابلة للتجاوز: عدّل الأصل في مكانه
- المصدر المعتمد هو آخر نسخة من الملف الأصلي في فرع العمل الحالي بالمستودع.
- نفّذ الإصلاح مباشرة على الملف الموجود في مساره الحالي داخل `فلاتر/`; لا تنشئ نسخة بديلة ولا تطلب استبدال الملف الأصلي لاحقاً.
- ممنوع إنشاء مجلدات مثل «إصلاحات» أو «إصلاحات 2» أو `patches` أو `fixed` أو وضع ملفات معدلة موازية خارج مساراتها الأصلية.
- الملف الجديد مسموح فقط عند ضرورة تقنية مثبتة، مثل اختبار أو مكوّن جديد، ويجب وضعه في المسار الطبيعي للمشروع لا كمجلد تسليم.
- لا تعتبر الأرشيفات القديمة أحدث من ملفات الفرع؛ افحص آخر Commit وGit diff قبل التعديل.

## طريقة العمل
- اقرأ `/AGENTS.md` و`/PROJECT_NOTES.md` وهذه التعليمات أولاً.
- تتبع تدفق البيانات كاملاً: الشاشة → الحالة → ApiService → الطلب → API response → model parsing → العرض.
- افحص أسماء الحقول وأنواعها والقيم الفارغة وحالات الفشل والتحميل، ولا تفترض تطابق نموذج Flutter مع Laravel دون مراجعة الطرفين عند الحاجة.
- حافظ على سلوك التسجيل وتعديل الملف الشخصي والاشتراكات والتنقل والإشعارات والبطاقات ما لم يكن التغيير مطلوباً ومثبت السبب.
- نفّذ أقل تغيير آمن، وشغّل `flutter analyze` والاختبارات المناسبة. إذا تعطل فحص بسبب بيئة أو أداة، اذكر ذلك دون اعتباره نجاحاً.

## سجل الدفعات
- أضف ملخص الدفعة في نهاية `/PROJECT_NOTES.md` الموجود؛ لا تنشئ سجل إصلاحات آخر ولا تستبدل الملاحظات السابقة.
- اذكر السبب الجذري، المسارات الأصلية التي تغيرت، الإصلاح، الاختبارات، وما لم يتم التحقق منه.

## ZIP عند طلب التسليم
- الحزمة تخص آخر دفعة فقط وتضم ملفات المصدر/الإعدادات/الاختبارات التي تغيّرت فعلياً في تلك الدفعة.
- احتفظ بالمسارات الأصلية بدءاً من جذر الأرشيف؛ لا تضف مجلداً عاماً باسم إصلاحات أو نسخاً بديلة.
- استبعد ملفات التعليمات والسجل وملفات الدفعات السابقة من ZIP المخصص لاستبدال ملفات التشغيل، إلا بطلب صريح.
- تحقق من سلامة الأرشيف ومحتوياته ومطابقتها لآخر Commit قبل إرسال الرابط.

## Git والنشر
- اعمل على فرع العمل المتفق عليه. لا تغيّر `main` ولا تدمج ولا تنشر إلى الاستضافة دون طلب صريح.
- لا تغيّر التبعيات أو إعدادات المنصات أو التوقيع إلا لضرورة مثبتة. وضّح الفرق بين فحوصات CI والاختبار على جهاز فعلي.


## قواعد واجهات التسجيل العربية والربط — إلزامية
- اجعل أسئلة التسجيل والملف الشخصي وتوقعات الشريك عربية طبيعية، لطيفة، حوارية وغير مملة؛ ابتعد عن الصياغة الإدارية الجامدة، مع الحفاظ على معنى السؤال ووضوح المطلوب وعدم إخفاء أي حقل أو شرط تحقق.
- استخدم في واجهة الجنس التسميتين «ذكر» و«أنثى» بدلاً من «رجل» و«امرأة». لا تغيّر معرّفات الجنس أو قيم قاعدة البيانات أو رموز API لمجرد تغيير النص الظاهر؛ حافظ على القيم الرقمية/المعرفات الحالية بعد التحقق من عقد الـAPI.
- اجعل اتجاه كل شاشة عربية RTL صراحة، بما في ذلك عناصر القوائم المنسدلة نفسها، نص العنصر المختار، قائمة الخيارات، نافذة الاختيار المنبثقة، حقل البحث داخلها، وعناصر الاختيار المخصصة. لا تعتمد على اتجاه الصفحة الأب وحده. اجعل المحاذاة من جهة بداية النص العربية (يميناً)، وحافظ على LTR للواجهات الإنجليزية.
- عند ربط أي قائمة، طابق قيمة الاختيار أو المعرّف مع القيمة التي يعيدها API حرفياً بعد التطبيع الضروري فقط. لا تعرض القائمة غير محددة إذا كانت القيمة محفوظة. حافظ على القيم القياسية للـEnums، وادعم القيم التاريخية القديمة بتطبيع متوافق دون تغيير سجلات المستخدمين القديمة.
- عند تعديل التسجيل أو الملف الشخصي أو توقعات الشريك، تتبّع المسار كاملاً في الاتجاهين: واجهة الإنشاء ← حالة النموذج ← ApiService ← Route/Controller/Request ← Model/Database، ثم Database/Resource ← ApiService ← واجهة تعديل الملف/توقعات الشريك. افحص تطابق الحقول والقيم، ولا تعتبر نجاح الإرسال وحده دليلاً على نجاح الاسترجاع.
- حافظ على مفاتيح API وأسماء الحقول والعلاقات كما هي ما لم تثبت ضرورة تغييرها مع تحديث كل المستهلكين المتأثرين. لا تغيّر صياغة العرض بطريقة تُرسل قيمة مختلفة للخادم.
- في حزم التسليم، استخدم أسماء ملفات وأرشيفات إنجليزية ASCII واضحة (مثال: WESAL_FIXES_14.zip) لتفادي مشاكل الروابط وأسماء الملفات العربية. بعد إنشاء ZIP، تحقّق من وجوده وحجمه وبنية الأرشيف وعدد ملفاته، وتحقق من مسار GitHub المباشر قبل إرسال رابط التحميل.


## دمج آخر نسخة لكل ملف — إلزامي
- عند وجود أكثر من نسخة معدّلة للمسار نفسه في فروع أو دفعات مختلفة، اقرأ سجل `PROJECT_NOTES.md` وقارن آخر تعديل لكل فرع، ثم اعتمد النسخة النهائية الأحدث لذلك المسار.
- لا تستبدل ملفاً حديثاً بنسخة فرع أقدم. انقل فقط الإصلاحات السابقة التي لا تزال مطلوبة وغير موجودة في النسخة الأحدث، مع دمجها داخل الملف الحالي.
- لا تعتبر ZIP أو فرعاً قديماً أساساً كاملاً؛ الدمج يكون ملفاً بملف بعد فحص التداخل والأثر على المستهلكين.
- يبقى `main` هو المصدر الأساسي بعد الدمج والتحقق. أي تعديل جانبي يجب أن يعود إليه قبل تسليم نسخة كاملة للنشر.
